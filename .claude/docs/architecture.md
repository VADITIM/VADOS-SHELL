# Architecture

Layers: `config → services → components → modules → windows → shell.qml`, plus `state/` (sideways) and `keybinds/` (state flips). Rules in `rules/architecture.md`; each layer's owner, imports, public interface and callers in `interfaces.md`. The product direction and its phases are `direction.md` (user, 2026-11-07).

## Engine map

How the subsystems of `direction.md` land in this tree:

| Direction | Here |
|---|---|
| Experience layer | `modules/` (taskbar, search, dashboard, settings), hosted by `windows/`; every surface, built or planned, is a row in `utils/Features.js` (§ Features) |
| Liquid interaction engine: orchestration, interruption | `components/Lifecycle.qml` + `utils/Phases.js` (transition phases), `state/Overlays.qml` (which surface is up), `components/Gesture.qml` (gestures and velocity), `components/Drift.qml` (scrolling) |
| Motion system | `config/Motion.qml` (tokens, `pace`), `utils/Liquid.js` (springs) |
| Geometry system | `utils/Geometry.js` (clamps, easing, mixing, splines), `Compositor.toScreen` (backend to screen coordinates) |
| State machine | `Lifecycle` per surface; `Overlays` for surfaces against each other; `Attention` for interruptions by notifications |
| Rendering system | `components/LiquidLayer.qml` (goo) and `components/Masked.qml` (masks), the only owners of effects and layers; `config/Rendering.qml` (quality, `blur`); the liquid primitives (`LiquidShape`, `LiquidBridge`, `EdgeFuse`, `Lobe`) are plain shapes drawn into a layer (§ Rendering system) |
| Platform adapters | `services/Compositor.qml` with `capabilities` and `level` (`utils/Platform.js`) |
| System services | `services/`, kept running by `services/Supervisor.qml` (§ Diagnostics and supervision) |
| Logs and diagnostics | `utils/Log.js` (the one logger), `utils/Diagnostics.js` (the report), IPC `diagnostics` |

## Boundaries

`interfaces.md` is the contract between layers. `tools/check-rules.py` holds it mechanically (`[layers]`):

- Import direction per layer (`LAYER_IMPORTS`): services import no state, components, modules, windows or keybinds; components import no state, services, modules, windows or keybinds; state imports no components, modules, windows or keybinds; config imports nothing from `qs`; keybinds import no components, modules or windows. Relative `import "../x"` counts the same.
- Services declare no visual type (`Item`, `Rectangle`, `Text`, `Shape`, windows, ...) and import no UI module (`QtQuick.Shapes`, `Controls`, `Layouts`, `Effects`, `Quickshell.Widgets`).
- Components read only component-level `Appearance` and `Motion` groups (`COMPONENT_TOKENS`). A component sized or timed by a feature takes `required property var look` and/or `pace` from the module: `ColorWheel` (settings), `EdgePull` (taskbar sizes, `Motion.reveal`).

## Features

`utils/Features.js` is the registry of every surface the shell draws, built or planned (rules in `rules/features.md`, contracts in `roadmap.md`). A row answers: `key`, `folder` under `modules/`, `root` (the module's root type), `surface` (`bar`, `mutation`, `overlay`, `lock`, `desktop`, `debug`), `origin` (the taskbar part it is born from: `edge`, `column`, `activity`, `idle`, `power`, `none`), `impact` (`ambient`, `glance`, `focus`, `takeover`), `needs` (capabilities of `utils/Platform.js`), `isBuilt`, and `layer` and `keepsTaskbar` on overlays.

The registry is load-bearing in three places:

- `Overlays.kinds` is `Features.overlayKinds()`: the built overlay rows with their layer and `keepsTaskbar`. A planned overlay has no kind, so `Overlays.open` ignores it and the taskbar is never gathered for a surface without a window.
- `tools/check-rules.py` (`[features]`) reads the rows (one per line) against the tree: every `modules/` folder belongs to a row; a built row has its root, and by surface kind its window, `shell.qml` entry (an overlay: its `OverlaySlot`) and IPC target; a folder with code but only planned rows fails.
- `tst_features` checks the rows (every field, valid values, unique keys and roots, `needs` are capabilities, a taskbar-born surface names its origin) and measures the ready time of the shipped enter engines against `Motion.budget.ready` (`Burst.isOpened` inside `focus`, `Mutate.isInnerShown` and the alert's `Reshape.isArrived` inside `glance`).

Things inside a surface are not rows; they are that surface's modules, listed in its catalogue (`utils/Lock.js` `modules`, `Settings.tabs`, `Activities.keys`).

**Adding a surface**, in this order (each step keeps the checker and the tests green):

1. The row, with `isBuilt: false`, and its folder under `modules/`. Its contract in `roadmap.md`.
2. Anything the engine lacks (a capability in `Platform.js` and the README table, a `Motion.liquid` character, an `origin`), each with its test and a line in `decisions.md`.
3. Data: services with a preview mock, runtime state in a `StateFile`, settings keys in `Schema.js`, `Config.qml` and the README.
4. Pure logic and catalogues in `utils/`, with a test.
5. The module root: state in as properties, requests out as signals, one `Lifecycle` for its phases, feature tokens in its own `Appearance` and `Motion` groups, every duration through `Motion.pace`.
6. The host by surface kind: an `OverlayWindow` plus its `OverlaySlot` in a `Variants` entry of `shell.qml` and an IPC target; or the taskbar module for a `mutation`; `LockWindow`; `WidgetWindow`.
7. The row flips to `isBuilt: true`; the preview loads it without a warning; README section; the contract moves from `roadmap.md` to `decisions.md`.

**Adding a module to a surface** is one catalogue row and one file in the surface's folder.

## Transition lifecycle

`components/Lifecycle.qml` runs one surface's phases: `idle → preparing → entering → active → exiting → idle`, with `recovering` for a reopen during the leave. The moves are a pure table in `utils/Phases.js` (`next(phase, event, canRecover)`); an event a phase does not accept changes nothing, so rapid or out-of-order input can never reach an invalid phase.

- The host sends `show` and `hide` (from `isShown`) and its animations send `prepared`, `entered`, `recovered` and `exited` from a final `ScriptAction`, so an animation that was stopped never reports.
- `show` during `exiting` is an interruption (`interrupted`): it goes to `recovering` when the host can rewind (`canRecover`), else back to `preparing`.
- `moving(from, to, event)` fires before the phase changes (the host captures its leave form there, while it still reads the old phase); `moved` fires after it (the host starts animations there).
- **Recovery**: a watchdog (`Motion.lifecycle.stuck`, longer than any real phase) runs only while a phase is moving. If it fires it logs `vados: lifecycle: <name> stuck in <phase>, settling` and sends `settle`: entering phases land on `active`, `exiting` on `idle`, and the host snaps its values to that end. No surface can stay orphaned half-open.
- Hosts: `Burst` (dashboard, search, settings, notifications; recovers by rewinding). Their `isActive`, `isLeaving` and `phase` read the lifecycle.
- **Every leave lands exactly once.** The hosts emit `landed()` through `land()` (guarded by `hasLanded`, reset when a leave starts), from the leave's `ScriptAction` or, when the watchdog settles a leave to `idle`, from `settle`. A settled leave still hands the taskbar back.
- **Leave geometry follows the screen.** At the leave start the host keeps its form with the frame it was drawn in (`heldForm`, `heldFrame`; Burst: seed point and form size). `leaveFrom` is `Geometry.refit(heldForm, heldFrame, frame)`, so a screen resized or a panel moved mid-leave reshapes the leaving body instead of drawing it in the old screen's coordinates. The enter already binds to the live geometry.
- **Overlays sees the phases.** Each overlay module exposes its `phase`; `OverlayWindow` reports it to `Overlays.reportPhase(key, screen, phase)` (§ Overlay engine).

## Compositor boundary

`Compositor` picks a backend once:

1. **hyprland**, when `HYPRLAND_INSTANCE_SIGNATURE` is set. It runs `hyprctl -j monitors` and `activewindow`, 60 ms after relevant socket2 events and every 2 s.
2. Otherwise it starts `driftwm msg --json subscribe`. The first `State` line selects **driftwm**. Each line is a full snapshot (camera, zoom, windows, outputs, fullscreen, pinned). Once driftwm is selected, a `Supervisor` restarts the stream with backoff whenever it exits (§ Diagnostics and supervision).
3. **generic**, when the stream exits before any `State` line (`hasNoCanvas`; the supervisor goes inactive and never retries). It reads `ToplevelManager.activeToplevel` and counts as covered only when fullscreen or maximized.

It publishes:

- `activeWindow`, screen-local and Y-down
- `focusedScreen`
- the raw `canvasState`
- `viewports()`
- the `canvasChanged` signal

Writes go out through `send([...])` / `action("spec")` as detached `driftwm msg` calls, only while `capabilities.windowControl` holds; elsewhere they go nowhere.

**Capabilities** (`utils/Platform.js`, the contract): features ask `Compositor.capabilities` and never which compositor runs. Each backend row answers every key, and claims only what the code implements:

- `activeWindow`, `fullscreenDetection`, `layerShell`: every backend (generic knows the active window only while it is fullscreen or maximized).
- `windowGeometry`, `focusTracking`: driftwm and Hyprland. Without them the taskbar hides only for covering windows and `focusedScreen` stays on the first screen.
- `windowControl`, `freeCanvas`, `windowMinimize`, `windowSnap`: driftwm (IPC by window id; minimize is `Confinement`'s parking, snap is its resize and move, both in Desktop mode).
- `workspaceManagement`: no backend yet (Hyprland workspace events only trigger a refresh).

`Compositor.level` is `core` (generic), `extended` (Hyprland: geometry, no window control) or `native` (driftwm: free canvas and control, so Desktop mode). `Confinement.canConfine` is `freeCanvas && windowControl`, `canMinimize` and `canSnap` add `windowMinimize` and `windowSnap` to Desktop mode, and `maximize()` and `fullscreen()` ask `windowControl`. The README "Compositor support" table is the user-facing copy; `tools/check-rules.py` fails when it and `Platform.js` disagree. Capability tests: `tst_platform`.

## Taskbar hiding

`TaskbarWindow.isCovered = Occupancy.isCovered(screen, Overlays.isHolding(screen))`, and `Taskbar.isRevealed = !isCovered || isSummoned`. Dwelling 0.3 s on the 3 px edge strip summons the bar and it leaves 0.2 s after the pointer does (`Motion.reveal.linger`); there is no drag (`EdgePull` ability: dwell drives the bead, `summoned()` calls `Taskbar.summon`).

## Taskbar side

`Config.data.taskbar.side` anchors `TaskbarWindow` to the left or right edge. The `Taskbar` module is always laid out for the left edge. On the right, `isMirrored` flips the whole module with an `Upright` scale of -1 around its centre, and every readable leaf flips back with its own `Upright`: task icons, idle glyphs, idle expansions, the clock, the title tip text and the carried icon. Pointer coordinates and `mapToItem` go through the transform, so carry and neck logic is unchanged.

**Compact idle column**: every idle circle's pointer area is a `FoldDrag` (`modules/taskbar/FoldDrag.qml`), a `Gesture` that calls `Taskbar.foldIdles(isFolding)` once a press travels `Motion.fold.threshold` up or down, and swallows the click that follows. Down folds, up unfolds. `foldIdles` closes any open idle and emits `compactRequested`; `TaskbarWindow` writes `taskbar.compact` to `shell.json` and feeds it back as `Taskbar.isCompact`. While compact, only idles with `isKeptCompact` (audio, power) stay `isPresent`; the others close their slot (`room`) and pop out, and `FoldDot` (a small liquid bead with three specks, top of the column) pops in. A click on it, or a drag up on it or any idle, unfolds. The compact column is the seed of the activity bar (`roadmap.md`). The input mask lives in the window (`inputZone`, placed from `Taskbar.inputWidth`), not in the transformed module. `Occupancy` checks the edge the taskbar is on.

## Activity pill

Data: `Activities` (service) is the activity catalogue: `keys` (`call`, `media`, `notifications`, `tray`), `liveKeys` and `order` (live first), the MPRIS track and controls, the Discord call from PipeWire stream nodes, `notificationCount` / `unreadCount` from `Notifications` and `trayItems` from `Tray`. `notifications` is live while anything is unread; `tray` is never live, so tray icons alone never make the pill active, but the wheel and `pin` reach it. State: `ActivityState` (`state/`) holds `mode` (`hidden` → `idle` → `active` → `expanded`), the screen it is expanded on and the lead. `CTRL + LEFT / RIGHT` (`GlobalShortcut` `activityPrevious` / `activityNext`, IPC `activity`) call `ActivityState.step` on the focused screen, clamped at both ends; `vados:activity` and IPC `activity toggle` expand or fold it (`toggle`, `fold`), `pin <key>` picks the lead, `current` returns it. The `notifications` activity has no expanded view: expanding the pill while the bell leads (a click, `CTRL + RIGHT`, `activity toggle`) opens the notifications menu (`Overlays.open("notifications", screen)`, § Notifications menu) and the pill keeps its mode; the wheel skips the bell while the pill is expanded, and pinning the bell folds it. It goes active by itself when the first activity starts and idle when the last stops; a forced state stays until then. An expanded pill stays expanded, with its lead pinned, until the user folds it: reading the last unread notification or a call ending does not fold it under the pointer. While the notifications menu is open on any screen (`isReading`, `Overlays.stack`), everything is marked read, arrivals included (deferred with `Qt.callLater`: marking read from the unread count's own change handler is a binding loop). `TaskbarWindow` maps `ActivityState.modeOn(screen)` (expanded only on its own screen, active elsewhere) and `leadKey` into `Taskbar.activityMode` / `activityLead`, and `activityModeRequested` / `activityLeadRequested` back. The taskbar asks to fold an expanded pill back to active when it hides, is eaten or goes away.

`ActivityPill` sits at `Taskbar.activityCenter`: the screen's vertical middle, kept below the task pills and above the idle column. Its body is one `LiquidShape` in the taskbar liquid (plus `EdgeFuse` for the fused style), sized by the `Reshape` ability from the state: bead (`activity.bead`), capsule (`activity.width × length`), or the lead's expanded size. Up to the capsule width the body is centred on the taskbar spine; wider, its left side stays at the capsule's left and it grows towards the screen, so it spreads out of the taskbar. `expansion` (0 to 1, overshooting) is its width progress; each expanded view hangs its own liquid off it, which gives each activity its own shape: `ActivityMedia` a disc head concentric with the root cap (`media.head`), `ActivityCall` two drops sliding out of the bottom past `Motion.activity.dropStart`, `ActivityTray` none. Each view gives its own `bodySize`, which `ActivityPill.expandedSize` takes for the lead (`views` by key), so adding an activity is a key in `Activities`, a face in `ActivityGlance` and one view file. `ActivityTray` (`activity.tray`): a dots badge, then one cell per tray item up to `columns` (the item's icon, or its initial on a disc without one); its width follows the item count; a click activates the item, a right click opens its menu, both through `Tray` at the cell's window position on `Taskbar.hostWindow`. The active face shows a bell or dots with the unread or item count (`countLimit`, then `+`). Running activities other than the lead hang under the active capsule as satellite droplets, each popping in on its own spot (a `Mutate` each, staggered outwards by `Motion.activity.stagger`) once the capsule has arrived. The active face (`ActivityGlance`) is one `Turn` per icon, the glyph first and the indicator a stagger later, so the icons never scale into one point together.

Expanded sizes are the base sizes times `activity.expanded.factor` (1.3, user 2026-11-11), with their own fonts (`expanded.label`, `expanded.body`), gaps and control sizes; the media lines fade at their far end instead of eliding (`Masked`, only while expanded), and `taskbar.windowWidth` is 480 so the larger views and the clipboard fit.

Order of a change: `Mutate` pops the pill in and out (hidden); faces leave over `faceLeave`, the far ones first (`Turn.leaveDelay`, `Motion.activity.leaveStagger`), while each expanded view is carried towards the spine with the body (`ActivityPill.carry`: `activity.carry` times one minus `expansion`); `Reshape` grows at once (OutBack, lead axis first, the other `lag` behind) or shrinks after `shrinkDelay` (InBack with `windUp`: a small swell, then sucked into the taskbar, the lead axis first and the other `shrinkLag` behind; the faces of the next state come only once it has landed, `shrinkArriveShare` 1), and on landing `Gulp` swells the body by `activity.gulp` (height by `gulpStretch` of it) and lets it ring out with `Motion.liquid.gulp`; faces enter on `Reshape.isArrived` (`arriveShare` of the move), expanded content staggered by `Motion.activity.stagger`, text through `TypedText`. Clicks: idle → active → expanded, expanded → active; the wheel rotates the lead. Mirroring: the expanded view keeps the mirrored layout (head at the edge); readable blocks (details, art, ring, glyphs) counter-flip with `Upright`. The pill body counts as a taskbar part for overlays (`liquidParts`), and its `reachRight` widens the input zone.

## Overlays absorb the taskbar

Search, settings and the dashboard sit on the overlay layer, above the taskbar, so their liquid can only react to the taskbar if they draw it themselves. `Overlays.open` calls `gatherTaskbar(screen)`: unless the taskbar on that screen is already away, it emits `taskbarGathering(screen)` and adds the screen to `awayScreens`. On that signal `TaskbarWindow` publishes `Taskbar.liquidParts()` (every shown pill body and idle circle, the gear included since 2026-11-09; none for `bare`) with `placeTaskbarParts`.

Both are in **edge-relative coordinates**: the taskbar's own left-edge layout, before mirroring, which equals the distance from the screen edge. Each overlay mirrors them itself from the live `taskbar.side`, so geometry never depends on when the layer-shell window re-anchors.

While away the taskbar is cut to opacity 0 and unrevealed, and the overlay's `Gather` (`components/Gather.qml`) draws the same silhouettes in its own `LiquidLayer` and pulls them into one point, where they goo into the overlay's body. The overlay emits `landed()` at the end of its leave; `Overlays.returnTaskbar(screen)` then brings the taskbar back unless another overlay is open on that screen.

- **Dashboard, search and settings**: `Burst` streams the parts to the taskbar column, where they form a new ball fused to the screen edge, which explodes along the overlay away from the edge.
- **Gather style** (`taskbar.gather`, a trial toggle in Settings > Settings, 2026-11-11). `merge` is the flow above. `shrink` never merges, in either direction. On the way in the pills are not held (`Taskbar.isHoldingParts` is off), so each one drops its elements, retracts to a circle and pops to 0 in place (`Mutate` `popLeave`), and the taskbar's liquid is cut only after `Motion.pill.shrinkHold`. Every overlay window passes `shouldStream: false` to its module and on to `Burst`, which then draws no streams and no gulp: its ball grows alone at the seed over `Motion.burst.grow` instead of `converge`, so the burst starts about 280 ms sooner. On the way out `Burst` never hands off (`shouldHandOff` needs `shouldStream`): the body collapses into its circle and slides into the edge as when a window covers the taskbar, nothing streams back, and once it lands the taskbar returns with its ordinary reveal, each pill popping in where it sits. The published parts are then unused. A swap between overlays still keeps the circle.

## Abilities

Animations are **ability components**: attached to an element, an ability watches the element's state and plays its own motion; the host sets state and binds to the ability's cues, never runs a timeline. One ability, one concern:

| Ability | State it plays | Use |
|---|---|---|
| `Turn` | enter, leave (`isShown`) | wraps a piece that comes and goes |
| `TypedText` | enter, leave, text change | text arriving on screen |
| `LabelReveal` | enter, leave (`isShown`) | the V/AS bar sweep: an accent bar grows across `sweepWidth`, the content opens under it, the bar retracts off the far edge; the leave is a cut (clip closes). Plays `<label> enter` / `<label> leave` |
| `Outline` | enter, leave (`isShown`) | a border tracing itself from the top-left corner along both sides to meet at the bottom-right (`Geometry.halfOutline`, `cutAlong`); the leave is its own faster fade. Plays `<label> enter` / `<label> leave` |
| `Drift` | wheel, touchpad scroll, keyboard reveal | declared inside a `Flickable`; the content glides to where the wheel sends it (§ Scroll drift) |
| `Press` | click (`isPressed`), hover or selection (`isRaised`) | `Press { target: item; isPressed: area.pressed }`, animates the target's `scale` |
| `Reshape` | size change (`targetWidth`, `targetHeight`) | the activity pill body: grow with overshoot, its own shrink (`shrinkEasing`, `windUp`, `shrinkLag`, `shrinkArriveShare`), `isArrived` cue for the faces |
| `Throw` | flight (`isThrown`) | one progress `share` 0 to 1 over `span` (`overshoot` lets it run past 1 and settle back); the host maps it onto a path (`Geometry.arcAt`) and a size; reset when recalled |
| `Gulp` | landing (`isLanded`) | a decaying swell (`Liquid.ring`, `Motion.liquid.gulp`) once a body lands after a shrink; the activity pill adds it to its body |
| `Mutate` | enter, leave (`isShown`) | pill pop, spread and inner reveal cue (`isInnerShown`), `departed()`; task pills spread, idle circles only pop (`hasSpread: false`); the taskbar enter is their staggered `Mutate`s. Task icons enter from the centre outwards: `isInnerShown` fires halfway through the spread, the centre icon turns in then, and each ring further out is deferred (`TaskItem.openingDelay`) so the outermost starts once the spread is full (`Mutate.spreadAfterInner`, at least `Motion.pill.elementStagger` per ring); icons added to an open pill enter at once. With `isArriving` (the taskbar taking over from a released burst) `Mutate` shows at full size at once (`arrive()`) |
| `EdgePull` | hover dwell, drag pull | the hidden taskbar's edge strip and bead; `summoned()` |
| `Rising` | idle (`isRunning`) | bubbles off an open body |
| `Gather` | absorb (`merge`) | taskbar silhouettes pulled into one point |
| `Burst` | enter, leave (`isShown`) | the dashboard, search, settings and notifications body born from the taskbar parts at the taskbar column, its root side a `Lobe` into the screen edge, bouncing out into its form; with `splitAt` and `splitGap` a walled body splits in two as its edge wave starts (`split`, `waveShare`, `isSplit`, `bodyPieces`, `splitTop`, `splitBottom`) and closes the gap first when it leaves; the cut lines carry the same wave as the outer edge, its crest swept across the gap on the outer head's share of the run (`cutLines`, `cutHead`, `cutWave`) and neck shut from their middle as the gap closes; publishes `visitor` while leaving; cues `isOpened`, `isActive`, `form`, `landed()` |

Abilities without visuals are `QtObject`s (`Press`, `Mutate`, `Reshape`), so attaching one never takes a slot in a `Row` or `Column`. A `Behavior` easing a property towards a state value (overlay dim, idle stretch, hover swell, taskbar inset and fuse) counts as an ability. Not yet an ability: the taskbar carry (drag) choreography in `Taskbar.qml`, whose droplet is `Carried`; right click has no animation.

## Liquid engine

One physical identity for everything liquid (user, 2026-11-06). Three parts, no feature has its own physics:

- **Material**: `LiquidLayer` (blur `melt` per surface, then the `Appearance.liquid` thresholds) is the only goo. Bodies are `LiquidShape`, `LiquidBridge`, `Lobe`, `EdgeFuse` and `Shape`s inside a layer.
- **Characters**: every spring, bounce and wobble is a named character in `Motion.liquid`, written the V/AS way (`components/29-physics-motion.md`), so a spring tuned here feels the same as one in VAD/OS Notes:
  - `response`: seconds of one undamped swing. Mass and elasticity in one number: heavier or softer is a longer response.
  - `damping`: damping fraction, below 1 (liquid always overshoots; `quirks.md`).
  - `expansion`: the launch speed, in swing amplitudes. A rise with 0 starts from rest; a ring's amplitude is its expansion.
  - Settling is derived from the two above (the envelope is `e^(−damping · 2π / response · t)`), never set on its own.
- **Maths** (`utils/Liquid.js`, pure functions on a character):
  - `rise(character, seconds)`: 0 → 1 with overshoot and settle; enters and bounces.
  - `ring(character, seconds)`: a wobble around rest after a kick; impacts and pops.
  - `arrival(character)`: seconds until a rise first reaches 1; choreography keys off it (the burst's wave start).
  - `pull(value, velocity, target, character, frameTime, Motion.liquid)`: one frame of the semi-implicit spring integrator (1/240 s substeps, 50 ms cap) for anything a finger drives.
  - `isMerged(wasMerged, closeness, neck)` and `neckKick`: the neck between two bodies merges past `neck.merge`, separates under `neck.separate`, and kicks the droplet by `mergeKick` / `separateKick`.

| Character | Plays | Was |
|---|---|---|
| `burst` | `Burst` width and height bounce | `bounceDamping`, `bounceCycles` |
| `crash` | `Burst` far-wall impact wobble | `impactDamping`, `impactCycles` |
| `pill` | `Mutate` pop of task pills (60 ms) | `Easing.OutBack` |
| `circle` | `Mutate` pop of idle circles and the fold dot (220 ms) | `Easing.OutBack` |
| `follow`, `dock` | `Carried` droplet following the finger, docking into its slot | `Motion.springs` |
| `droplet` | `Carried` stretch | `Motion.springs.wobble` |
| `neck` | taskbar carry neck merge and separation | `carry.joinShare`, `snapShare`, `joinKick`, `snapKick` |

Closed-form rises and rings run on an ability's own clock (a linear phase in seconds), so they stay abilities; `pull` runs in a `FrameAnimation`. Leaves are not springs: they keep their own faster easing (`Mutate` InBack), as the animation rules require. A new liquid surface (alerts, clipboard, lock) picks a character or adds one; it never writes `Math.exp` itself.

## Rendering system

Rendering is separate from state and transitions: a host says only whether a surface is shown (`isShown`, its opacity); the rendering components decide which passes run. Two components own every effect, layer and mask in the shell (`tools/check-rules.py`, rule `rendering`); modules and other components compose them.

| Component | Owns | Passes (full) | Passes (lite) | Runs while |
|---|---|---|---|---|
| `LiquidLayer` | the goo: blur + threshold of its `shapes` | shapes texture, blur (`MultiEffect`, `blurMax` = `Rendering.blur(melt)`), blurred texture, rim, fill and core threshold passes, a flattening layer when `fillAlpha < 1` (always: `panelAlpha` 0.94); rim and fill colour textures | shapes texture, fill texture and the core threshold pass only | `isShown && opacity > 0` (`isRendering`); off is `visible: false`, textures not `live`, blur and threshold layers disabled; the colour surfaces are `ShaderEffectSource` textures, never `layer.enabled` (see `quirks.md`) |
| `Masked` | an alpha mask: content cut by the shape in `mask` | mask layer, content layer, one mask pass | same (a mask is layout, not decoration) | it is visible and its opacity > 0 |

Cost: every pass covers the component's whole area and re-renders in any frame where something inside it moves; static frames reuse the textures. A full liquid is about six full-area passes (blur is several downsampled levels), lite two.

| Instance | Area | Shown (`isShown`) |
|---|---|---|
| Taskbar `liquid` | taskbar window | `true`; stops at opacity 0 (bare style, taskbar away) |
| Taskbar `tipLiquid` | taskbar window | bare style while the title tip is up (before 2026-11-07 it ran empty, always) |
| Extension | taskbar window | while the extension is grown; stacks over the taskbar liquid then |
| Search, Dashboard | full screen | `burst.isActive` (enter to landed) |
| Settings | full screen | `launch.isActive`, opacity `launch.material` (0 in the bare style) |
| Best match avatar (`Masked`) | avatar | while the profile picture is loaded and the avatar is shown |

Cheap and kept in modules: `clip` (a scissor rectangle; search body, list and rows, the name pill, dashboard panels, idle pills, the title tip, the network page), plain `Rectangle` dim, and `Shape`s (`CurveRenderer`; paths re-processed on the render thread when their points change). Blur behind overlays is the compositor's (layer rules).

**Quality** (`rendering.quality`, `config/Rendering.qml`): `Rendering.isLite` and `Rendering.blur(radius)`, the one precedence function for blur, like `Motion.pace` for durations. Under lite the liquid keeps its shapes and threshold, so bodies, necks (`LiquidBridge`) and lobes keep their outlines; it loses the rim line and the soft fusion of bodies that only touch through the blur.

| | full | lite |
|---|---|---|
| motion normal | everything | no blur; motion as usual (bubbles still rise, cheap without blur) |
| reduced motion | blur; transitions instant, no bubbles, splashes or crests | the cheapest: instant and no blur |

Precedence: shown (`isShown`, opacity) gates every pass; quality decides which passes; motion only decides timing. Quality never changes durations and reduced motion never changes passes.

## Clipboard history

The clipboard history is a face of the activity pill (`clipboard` row, `surface: "mutation"`, `origin: "activity"`, `impact: "focus"`). Data: `Clipboard` (service) runs `wl-paste --watch python3 scripts/clipboard.py read <image folder> <images|text>` under a `Supervisor` while `clipboard.enabled` is on (the default). For each copy the script drains its stdin, skips `CLIPBOARD_STATE` `nil`, `clear` and `sensitive`, asks `wl-paste --list-types`, reports a skip when `x-kde-passwordManagerHint` is `secret`, a file entry for `text/uri-list`, an image only when no text is offered (saved by its hash under `~/.cache/vados/clipboard/` with `clipboard.images`, else skipped), and text otherwise; one JSON line each. `utils/Clipboard.js` turns a line into an entry (kind, secret flag), adds it newest first without duplicates (the same key moves up and keeps its pin), trims the oldest unpinned past `clipboard.size`, and keeps secrets out of what `StateFile` `clipboard` writes; entries that arrive before the file has loaded are merged with it. Picking runs `wl-copy --type <mime>` with the text on stdin (never on the command line), or `wl-copy` reading the image file; the copy comes back through the watcher and only moves the entry up. Images that leave the history are deleted.

State: `ActivityState.clipboardScreen` (`toggleClipboard`, `closeClipboard`, `isClipboardOn(screen)`, needs `Clipboard.isEnabled`). Opening it folds an expanded pill; expanding an activity or stepping the pill closes it. `TaskbarWindow` maps it into `Taskbar.isClipboardOpen` / `clipboardSize`, raises the taskbar over a fullscreen window while it is open, closes it when the taskbar hides (`clipboardCloseRequested`), and hosts `ClipboardHistory` over `Taskbar.clipboardRect` (the pill's `spreadRect`).

Body: the pill's `face` is `clipboard` (an alert still wins), `Reshape` grows to `Appearance.clipboard` with `Motion.clipboard` (grow 420 ms OutBack, `lag` 70, `arriveShare` 0.5: ready at about 280 ms, measured in `tst_features` against the focus budget), its corners capped at `clipboard.radius` while `isClipboardBody` holds. While the lead activity is live, a bump (`clipboard.bump`, popped by a `Mutate`) rides at the far end of the header row, sunk `bumpOverlap` into the body, with the lead's glyph (`Appearance.activity.glyphs`); hovering it extends it `bumpReach` to the right, a click expands that activity (which closes the clipboard), the wheel rotates the lead.

Content (`ClipboardHistory`, `ClipboardRow`): a header (badge, typed `CLIPBOARD`, count, trash while anything is unpinned), then six row slots plus one above and one below. Slot `s` shows `shown(entries)[first + s]`; the wheel or a vertical drag moves `first` and plays the move as `shift` easing back to 0, so rows glide instead of jumping. One `Gesture` over the list decides on crossing: sideways swipes the row under the press (past `Motion.clipboard.swipe` or `fling` removes it), up and down scrolls; a tap copies the row and folds the pill. Rows enter from the centre outwards (`stagger` per ring) and leave top first (`leaveStagger`), clipped by the shrinking body. Kinds: text (lines glyph), link (accent), file (names from the URI list, `+N`), image (thumbnail), secret (lock and dots). Overflowing labels fade at their far side (`Masked`), mirrored with the taskbar side through `LayoutMirroring`. It folds `Motion.clipboard.linger` after the pointer has been in it and left (the bump counts as inside). Pointer only; search waits for a keyboard owner.

## Screenshot and recording

`services/Capture.qml` owns both. Paths, names, the clock and the recorder choice are pure (`utils/Capture.js`, `tst_capture`). The save folders are `capture.screenshots` and `capture.recordings` (Settings > Settings), where `""` is `$XDG_PICTURES_DIR/Screenshots` (else `~/Pictures/Screenshots`) and `$XDG_VIDEOS_DIR/Recordings` (else `~/Videos/Recordings`); `~` is home.

**Screenshot** (`screenshot` row: `surface: "overlay"`, `origin: "activity"`, `impact: "focus"`, `layer: 2`, `keepsTaskbar: true`). PRINT (`vados:screenshot`, IPC `screenshot shoot`) calls `Capture.shoot(focusedScreen)`, which runs `grim -o <screen>` into the Quickshell cache **before** anything is drawn, so the frame holds the screen as it was. On `shot(screen)` `Shortcuts` opens the overlay; `ScreenshotWindow` passes the frame (`file://…?<frameStamp>`, uncached) to `modules/screenshot/Screenshot.qml`. The overlay sits above every other layer and keeps the taskbar: the frozen frame already shows it, and gathering it would make it animate back after every shot.

The module is one `Lifecycle` (`name: "screenshot"`): enter fades `presence` in over `Motion.capture.dim` (the frame is the screen, so only the dim reads), leave fades it out over `Motion.capture.leave`. Layers, bottom up: the frame, the dim (`Appearance.capture.dim`), a full-screen `InkCanvas` (ink is drawn anywhere, so moving or resizing the area keeps it), `cutArea` (the selection, clipped: the frame again plus `InkCanvas` with the strokes, both offset by the selection so they line up), the accent outline, the size chip (frame pixels), the eraser ring, the handles (every shape's corners, a line's ends, the area's corners under select), one `Gesture` for every drag, then the `Toolbar`. A drag decides on crossing, in this order: a shape handle reshapes that shape around its opposite corner (select, shape; `Ink.grabOf`, `reshaped`), an area corner resizes the area (select; `resized`), a shape's outline carries it (select; `shapeAt`, `shifted`), inside the area moves it (select), paint and shape draw and erase erases anywhere; otherwise a new selection, which falls back to the old one if it stays a sliver. A tap outside the area centres the area there (`centeredAt`), never closes. Every point is copied (`Ink.pointOf`) before it is kept: `gesture.pressPoint` is a value-type reference that follows the next press. Selections are clamped to the screen (`Ink.clampInto`); a sliver under `capture.smallest` is no selection.

`Toolbar` is a copy of the activity pill that mutates into the tools. The taskbar publishes the pill's place per screen (`Taskbar.activityPlace`: spine x, centre y, current body size, the glyph of an active face) through `ActivityState.place`; the window reads `placeOn(screen)` into `pillSpineX`, `pillCenterY`, `pillSize`, `pillGlyph`. The toolbar is its own `LiquidLayer`, sized to the toolbar, never full screen: its body starts at exactly the pill's size over the pill in the frozen frame, showing its glyph, and a `Reshape` grows it to `capture.toolbarThickness` (the pill width) × the tools' length along the taskbar over `Motion.capture.grow`, while the glyph fades and the tools (`Ink.tools`: select, color, paint, erase, shape) pop in from the middle outwards. It is shown and usable from the first frame of the screenshot. Color pops a `ColorWheel` out of the pill in a `LiquidShape` that travels and grows from the color tool to its panel (`wheelShare`); shape buds droplets beside its tool (`Turn` presence driving a `LiquidShape` reparented into the toolbar's liquid), so both goo off the body. The toolbar mirrors with the taskbar side (`Scale` and `Upright`).

Keys: Escape closes; Ctrl+C or Enter grabs `cutArea` at the frame's pixel size (`grabToImage`, no selection means the whole screen), the window saves it to `Capture.cutPath()` and `Capture.deliver` copies it into the folder and onto the clipboard (`wl-copy --type image/png`), announces `ActivityState.copiedNotice` (COPIED, alert source `screenshot`) through `Attention.announce`, then the overlay closes; Ctrl+Z undoes a stroke; Tab and Shift+Tab cycle select, paint, erase, shape; arrows nudge the selection (`nudge`, with Shift `nudgeFar`).

**Recording** is an activity (`Activities.keys` `recording`, live while `Capture.isRecording`; left out of `order` otherwise, so the wheel never reaches it idle). SHIFT+PRINT (`vados:record`, IPC `recording toggle`) calls `Capture.toggleRecording`. The recorder is probed once at start: `gpu-screen-recorder` (`-w <screen> -f 60 -a default_output`, can pause with SIGUSR2) before `wf-recorder` (no pause); SIGINT stops and saves. The command runs through `sh -c 'mkdir -p … && exec …'`, so the process signalled is the recorder itself. The clock ticks per second only while recording and not paused.

`ActivityState` pins `recording` as the lead when it starts, wakes a hidden or idle pill to active and calls `Attention.announce` with a notice (`isNotice: true`, summary `RECORDING NOW`, source `recorder` in `utils/Alerts.js`, `expireTimeout` `Motion.capture.announce`), so the pill grows into the alert and after 1.3 s shrinks into the recording face: `RecordDot` (a pulsing dot, a pause glyph while paused; the pulse is idle motion, off under reduced motion) and the clock (`ActivityGlance`). A click on that face pauses or resumes (when the recorder can); a hover of `Motion.capture.dwell` expands it into `ActivityRecording` (state, clock, pause or resume, stop), and once hovered it folds back `Motion.capture.linger` after the pointer leaves. Stopping folds an expanded recording pill and gives the lead back. A tap on the notice only dismisses it.

## Alerts

An alert is a face of the activity pill, not a window of its own (`alerts` row, `surface: "mutation"`, `origin: "activity"`, `impact: "glance"`). Data: `Attention.peek`. `TaskbarWindow` keeps the peek for its own screen while its taskbar is not away (`window.peek`) and maps it two ways: `Taskbar.isAlerting` / `alertSize` turn the activity pill's `face` to `alert`, so `Reshape` grows the same body to `Appearance.alerts` (`Motion.alerts`: grow 300 ms OutBack, `lag`, `arriveShare` 0.5, ready at about 195 ms, inside the glance budget); and `Alerts` (`modules/alerts/Alerts.qml`) gets the peek, the pill body rect (`Taskbar.alertRect`) and `isBodyShown` (`Taskbar.isAlertShown`, the pill's `Reshape.isArrived`) and draws the content over that body: the source badge (a ring and glyph in the source tint), the source label (caps, `+N` for a batched peek), the summary and the body typed in (`TypedText`, clipped by `Alerts.clip`), each a `Turn` staggered by `Motion.alerts.stagger`. The leave is the faces leaving over `faceLeave` while the pill shrinks back after `alerts.shrinkDelay` (`isAlertBody` keeps the alert shrink timing, and the expanded views' `expansion` at 0, until the body has arrived back).

The source comes from the catalogue `utils/Alerts.js` (`sources`: key, label, glyph, tint, desktop ids): the notification's desktop entry, then its app name, each as given and without a `.desktop` suffix, first against the ids, then as words against the keys (`WhatsApp Web` is WhatsApp); anything else is `generic` with the app name as label, a bell and the accent. Adding a source is one row.

Input: a `Gesture` over the body. The content follows the finger sideways (`slide`, fading out over the body width); a release past `Motion.alerts.swipe` or faster than `fling` throws it out and asks `dismissRequested` (the window calls `Attention.dismissPeek()`: the notification stays in `Notifications.list`, never lost); a shorter one settles back. A tap asks `openRequested(lead)`: `Notifications.open` invokes the `default` action, else runs the desktop entry, and the peek is dismissed. While the taskbar is hidden by a window (`isCovered`), only the activity pill is shown for the alert and the input zone widens to it; while an overlay holds the taskbar or the extension eats it, no alert is drawn.

Hover (user, 2026-11-11): a `HoverHandler` on the body, live only while the content is shown, sets `isExpanded`. `bodySize` then becomes the whole content, measured by hidden `Text`s before anything types: as wide as the header (label and summary at the open sizes `Appearance.alerts.openLabel`, `openTitle`) beside the badge or the unwrapped message across the body need, between `Appearance.alerts.width` and `expandedWidth` (the full `expandedWidth` with an image); as tall as the header block (badge or wrapped summary, `titleLines`), then `sectionGap` and the message wrapped across the full inner width from below the badge (`bodyLines`), then `imageGap` and the notification's `image` at the full inner width (up to `imageHeight`). The pill's `Reshape` grows to it with the alert timing and the liquid body keeps `Appearance.alerts.radius` corners instead of turning round; `ActivityPill.hasAlertArrived` keeps `isAlertShown` true while the body reshapes, so the faces never leave mid-hover. Nothing jumps: badge and header stay at their resting offsets from the top (`badgeTop`, `columnTop`, centred only while the body is smaller than at rest), the header grows its font and the message glides from beside the badge to below it (`Motion.alerts.settle`), the text types what was missing within `Motion.alerts.typeBudget` (`TypedText.typeBudget`) and untypes it fast on retract while keeping its lines until the untype is done, and the rows ease their heights. The image pops in as a circle (`bloom`, OutBack over `imagePop`), then opens to its rectangle and its corners settle to `imageRadius` (`corner`, `imageCorner`); it leaves over `imageLeave`. The change of `isExpanded` asks `holdRequested`; the window calls `Attention.holdPeek`, which stops the expiry while held (a peek placed meanwhile does not restart it) and on release lets an alert that is not urgent linger `Motion.attention.linger` (1.2 s) after the body has retracted. `dismissPeek` clears the hold.

## Notifications

`services/Notifications.qml` owns `org.freedesktop.Notifications` through a `NotificationServer` inside a `LazyLoader`, active only while `notifications.enabled` (default off, `decisions.md`). Every arriving notification is tracked and unread until `markRead`; `list` is newest first. Notifications are compared by `id`, never by object identity (`quirks.md`). `Shortcuts` binds to `Notifications.isServing`, which creates the singleton at startup (`quirks.md`).

The history: every notification the server accepts is also kept as a plain entry (`utils/History.js`: `key`, `id`, `appName`, `desktopEntry`, `summary`, `body`, `urgency`, `icon`, `time`) in the `StateFile` `notifications` (`~/.cache/vados/notifications.json`), newest first, at most `notifications.history`; transient notifications are not kept, and an icon is stored only as a file path (an `image://` the server hands out dies with the notification). `forget(entry)` removes one and dismisses its live notification, `openEntry(entry)` opens the live one or runs its desktop entry, `clear()` dismisses everything and empties the history.

Entry points: the activity pill's bell and `SUPER + N` (`vados:notifications`, IPC `notifications toggle | close`) open the notifications menu; IPC `activity toggle | close | pin <key> | current` and `notifications enable | disable | status | count | clear`.

## Notifications menu

`NotificationMenuWindow` (overlay, layer 1, exclusive keyboard) hosts `modules/notifications/NotificationMenu.qml`, the `notifications` row (`origin: "column"`, `impact: "focus"`). It is built like search: a `Burst` column out of the taskbar column with a traced wall (`Appearance.notifications.wall`, `[share of the form width, y share]`, converted to offsets from the far edge), `widthShare` 0.25 of the screen, and the same leave and taskbar hand-off. While a sending app is installed (`Transfer.isAvailable`) the burst splits (`splitAt` 0.64, `splitGap`; `Burst` § split below): the upper body is the history, the lower body the send tray. The wall dips to half the width at the split, so each body's corner there is the wall's curve and only a short cut is straight; without a sending app the body stays whole (`wholeWall`, `wholeListEnd`).

- **History**: a `ListView` of `NotificationRow`s (`Notifications.history`): the app icon (or the source glyph in its tint from `utils/Alerts.js`), the app label and its reveal bar in the app's tint and the group and its bar (the summary) in that tint faded to `groupFade`; the tint is the catalogue's, else the icon's own colour (an invisible `Canvas` draws the loaded icon at `tint.sample` and `utils/Tint.js` picks its most colourful hue), else the accent; both typed in (`TypedText`, the label reveal of the sketch), the message on one line; each a `Turn` staggered by `Motion.notifications.stagger` (up to `staggerRows`). A tap opens it and closes the menu, a sideways `Gesture` past `Motion.alerts.swipe` or `fling` forgets it (deferred past the release), `NOTHING NEW` when empty.
- **Bubbles**: the trash (clear all) and mute (do-not-disturb, through the window to `Attention.setQuiet`) bud out of the upper wall at `bubbleShares`, the gear (next sending app, through the window to `Config.setSendApp(Transfer.nextApp())`) out of the lower wall at `gearShare` with the app's name beside it. Each is a `Turn` (`isFlipping: false`) whose `presence` drives a `LiquidShape` reparented into the burst's liquid: it grows from the wall's x (`Burst.wallXAt`) out to `bubbleReach` past it, so the goo necks it off the wall.
- **Send tray**: the devices from `send.devices` (`Transfer.devices`) as circles with their names, then SEND. A tap on a device chooses it; SEND closes the menu (the file chooser opens under an exclusive overlay otherwise) and calls `Transfer.send(peer)`. The send tray enters once the split has passed `Motion.notifications.sendShown`.
- **Keyboard**: zones `list`, `actions` (trash, mute), `send` (devices, SEND, gear); Tab and Shift+Tab cycle them, Up and Down move in the list and leave it at its ends, Left and Right move in a zone, Enter or Space presses, Delete or Backspace forgets a row, Escape closes.

`services/Transfer.qml` sends files with the app named by `send.app` from the catalogue `utils/Senders.js` (`senders`: key, name, binary; `sendCommand`, `devicesOf`, `nextOf`). It probes once at start which binaries are installed; `send(peer)` asks `services/FileChooser.qml`, which runs `scripts/pick-files.py` (the XDG desktop portal `FileChooser.OpenFile`, so the user's file chooser opens; it prints one path per line) and then the app once per file, `blip --peer=<peer> --file=<path>`, or `blip --file=<path>` with no device chosen.

## Overlay engine

`state/Overlays.qml` is the one registry for full-screen surfaces (it replaced `Visibilities`, 2026-11-07). `kinds` holds each overlay and its `layer` (search, settings and dashboard share layer 1); it is `Features.overlayKinds()`, the built overlay rows of the registry (§ Features). State: `screens` (key → screen), `stack` (opening order; `top` is the last), `awayScreens` (screens whose taskbar is gathered), `taskbarParts`, `visitors` (screen → overlay → leaving ball).

- `open(key, screen)` closes every overlay on the same layer or below, gathers the taskbar (once per screen: a switch keeps the first gather's parts), and pushes the key on the stack. An overlay that `keepsTaskbar` (the screenshot) neither gathers the taskbar nor waits for a swap: it opens at once over whatever is leaving under it. `close`, `toggle`, `closeTop` (Escape, IPC `overlay close`).
- `ownsKeyboard(key, screen)`: only the top overlay takes exclusive keyboard focus.
- `returnTaskbar(screen)` (an overlay's `landed()`) brings that screen's taskbar back only when no overlay is left on it, whichever screen the next overlay opened on.
- `placeVisitor(key, screen, ball)` / `visitorOn(screen)`: each leaving overlay owns its own entry, so one leaving never erases the other's ball.
- `phases` (screen → overlay → lifecycle phase, idle ones dropped), `phaseOf(key, screen)`, `isSettled(screen)` (every surface on it is `active` or gone). When a surface reports `idle`, `Overlays` calls `returnTaskbar` for its screen: the taskbar comes back once nothing is on the screen, even if a `landed()` was lost.
- `keepScreens(names)` (from `shell.qml` on `Quickshell.screens` changes) closes overlays on screens that went away and drops their away flag, parts, leaving balls and phases, so an unplugged monitor leaves no exclusive keyboard or gathered taskbar behind.

`windows/OverlayWindow.qml` is the window side: a full-screen `PanelWindow` on the overlay layer, namespace `vados-<key>`, keyboard from `ownsKeyboard`, with `isOpen`, `parts`, `requestClose()`, `land()` and `placeVisitor()` for its module. `SearchWindow`, `SettingsWindow` and `DashboardWindow` are an `OverlayWindow` plus their module. A new overlay is a built overlay row in `utils/Features.js` and an `OverlayWindow` (§ Features).

**Overlay windows exist only while wanted** (2026-11-11). `shell.qml` holds no overlay window directly: per screen and overlay it holds an `OverlaySlot` (`windows/OverlaySlot.qml`) with the window as a component. The slot builds it through a `LazyLoader` when `Overlays.isWanted(key, screen)` (open there, or its phase is not idle yet) and destroys it when that ends and the window is no longer `isPresent` (the dashboard's last bubbles), one event-loop turn later (`Qt.callLater`), so the window is never deleted inside its own leave. The window is built closed (`isComplete` false) and opens in its `Component.onCompleted`, so `Burst`, the dim and the focus handlers see a real closed-to-open change. An overlay nobody opened costs nothing: no QML objects, no render thread, no GL context, no textures. Measured cost of building on open: 5 to 28 ms until the window is complete, first frame 26 to 61 ms after the trigger (was 20 to 39 ms with windows kept), inside `Motion.budget.ready.focus`. `tools/check-rules.py` (`[features]`) fails when a built overlay's window is not inside a slot with its key.

## Gesture engine

`components/Gesture.qml` is a `MouseArea` ability for every drag: `threshold` (default `Motion.gesture.slop`), axes, `dragButtons`; it tracks `travelX/Y` from `pressPoint` and a smoothed velocity (`Motion.gesture.velocityBlend`). Signals: `moved` every move, `crossed` once when the travel passes the threshold, `thrown(travel, velocity)` on release after a drag, `tapped(mouse)` on a release without a drag, `ended` always. Built on it: `FoldDrag` (fold on crossing), `EdgePull` (pull length on `moved`, summon on `crossed`), the task carry in `Taskbar` (`crossed` picks up, `moved` carries, `thrown` lands, `tapped` activates or closes). Named `Gesture` because `Drag` is QtQuick's attached type and wins inside `qs.components` (`quirks.md`).

## Scroll drift

Every scrolling view in the shell (the search list, the notifications menu, the task manager, the network page, the settings lock cards) declares a `Drift` inside it. Qt's own wheel moves a `Flickable` in one rigid step; `Drift` (a `WheelHandler`) takes the wheel instead and moves the content through `Liquid.pull` with the `Motion.liquid.drift` character (near-critical, no visible overshoot), so the content keeps its velocity across notches and settles softly. A mouse notch adds `Motion.drift.notch` pixels to the goal (`notchAngle` per notch, high-resolution wheels proportional); notches in a row add up while the glide is running. A touchpad's pixel deltas move the content directly (the finger drives) and, on the scroll's end, it glides on for `Motion.drift.glide` seconds of its last velocity. Keyboard reveals glide too: `glideTo(value)` from a target, `glideAround(move)` around a jump such as `positionViewAtIndex` (the jump is made, read, undone and glided to). The goal stays inside the content's bounds, a move made by someone else (a drag, a model change) is adopted, a drag stops the glide, and under reduced motion every glide is instant. The frame loop runs only while gliding. Drags and flicks stay Qt's own.

## Attention engine

`state/Attention.qml` decides whether a notification may interrupt (`rules/interaction.md`). It listens to `Notifications.received`; `mayPeek` lets critical through always, holds low always, and holds normal ones under do-not-disturb (`attention.doNotDisturb`) or while the active window is fullscreen. Admitted notifications gather for `Motion.attention.batch` and then become one `peek` `{ notifications, isUrgent, screen }` on the focused screen, which expires after the longest own timeout (`expireTimeout`, seconds) or `Motion.attention.peek`; urgent peeks stay until dismissed, and a peek drops notifications as they are dismissed. The alerts draw `peek` out of the activity pill (§ Alerts); held notifications stay unread, so the activity pill turns active with the bell and their count (§ Activity pill).

## Configuration

`shell.json` (`~/.config/vados/shell.json`) is read and written only by `config/Config.qml`, whose `JsonAdapter` exposes it as `Config.data`. What a valid file is lives in one pure table, `utils/Schema.js`: each key (`group.name`) with its `type` (`boolean`, `string`, `colour`, `names`), its `fallback` and, for enumerations, its `choices`; plus `version` (1) and `migrations` (step `n` turns version `n` into `n + 1`).

Load: `FileView.loaded` → next tick `Config.repairLoaded()` → `JSON.parse(file.text())` → `Schema.repair(raw)` = `migrate` (version 0 when missing, a broken version reads as 0, a newer one is read but never written) then `validate` (defaults first; each known key with a valid value is kept; a wrong type or a value outside its choices falls back with a problem; unknown groups and keys are reported and dropped). `Config` assigns the clean values that differ, logs each problem once (`console.warn("vados: config: …")`, with the file's path), and calls `writeAdapter()` only when `shouldWrite` (a migration or a repair). The written file validates clean, so the reload it triggers writes nothing. A file that is not JSON is logged and left alone; the settings stay as they were.

Setters: each `set…` calls `accept(key, value)`, which asks `Schema.findProblem`; an invalid value is refused, logged, and the current value kept. `check-rules.py` holds the schema, the adapter (same keys and defaults) and the README Settings rows in step, and fails a setter that assigns a key it did not `accept`.

The preview and the tests use the `Config` mock in `tools/preview/play.py`; `Schema.js` itself is tested pure in `tst_schema`.

## Persistence

`services/StateFile.qml` is a reusable `Scope` for runtime state: `name` → `~/.cache/vados/<name>.json` as `{ version, data }`, `values` (defaults merged with the file), `update(next)` (debounced `Motion.store.write`), `flush()` (also on destruction), `isLoaded`. A file without `version` is read as plain data; a file that does not parse is copied to `.corrupt`, another version to `.version<N>`, and the defaults are used. Users: `Apps` (launch history, still `apps.json`), `Confinement` (`desktop.json`: parked windows).

`Confinement` waits for `isReady` (state loaded and a driftwm canvas seen) before `recover()`: saved parked windows that still exist are adopted in Desktop mode (so `enter()` never parks them a second time at their parking spot), or put back in Canvas mode; windows that no longer exist are dropped. Every park and restore is saved.

## Diagnostics and supervision

Rules in `rules/reliability.md`.

**Logging.** `utils/Log.js` is the one logger (a `.pragma library`, so one instance per engine and one ring for the whole shell). `Log.info` / `warn` / `error(subsystem, message)` print `vados: <subsystem>: <message>` through `console.*` (which Quickshell sends to its output and the journal). A message already printed within `Log.repeatWindow` (5 min) is not printed again: its entry counts `repeats` and keeps the `last` time, and the first print after the window adds `(repeated N more times)`. The last `Log.capacity` (100) entries stay in memory (`recent()`); the repeat memory is pruned past the same bound. Subsystems in use: `lifecycle` (stuck phases), `config` (schema problems), `weather`, and each supervisor's name.

**Supervision.** `services/Supervisor.qml` is a reusable non-visual type (like `StateFile`), placed beside the work it keeps alive:

- `process`: a `Process` it owns. It sets `running` itself (the host declares no `running:`), starts it while `isActive`, stops it and cancels a pending restart when `isActive` goes false. A stop it asked for is never a failure, even when the process exits only after the surface was shown again (`isStopping`; it then starts at once).
- When the process stops while active, one zero-length timer later (so the `exited` code is in whichever order Quickshell emits `exited` and `runningChanged`) it is a failure: `exited with code N`, or `failed to start` without an exit.
- `fail(reason)`: `failures` (in a row) goes up, the delay is `Backoff.delayOf(failures, Motion.supervision)` (`base` 1 s doubling by `factor` up to `cap` 60 s), it logs `<reason>, restarting in N s` and holds (`isHolding`, status `waiting`). When the hold ends it restarts the process (`restarts` goes up) and emits `restarted()`.
- `succeed()`: after `Motion.supervision.healthy` (30 s) of running, or when the host reports success, `failures` resets and a recovery is logged (`recovered after N failures`).
- Without a `process` it supervises any retried work: the host calls `fail` and `succeed` and redoes the work on `restarted()` (`Weather`'s fetches).
- `status`: `stopped` (inactive), `waiting`, `failing` (restarted, not yet healthy), `healthy`. Every supervisor enrolls in `services/Supervision.qml` on creation and leaves on destruction.

| Service | Supervised | `isActive` |
|---|---|---|
| `Compositor` | `driftwm msg --json subscribe` | not Hyprland and the probe found a canvas (`!hasNoCanvas`) |
| `Network` | `nmcli monitor` | always (the taskbar shows the network) |
| `Removable` | `udevadm monitor` | always (the taskbar shows removable drives) |
| `Traffic` | `ping` | `Traffic.isActive` (dashboard open) |
| `Weather` | the geocoding, IP and forecast requests (no process) | `Weather.isActive` (dashboard open) |

Not supervised: one-shot queries that a poll already repeats (`Hardware` probe, `Network` and `Removable` queries, Hyprland `hyprctl`); a failed run is simply retried by the next poll.

**Diagnostics.** IPC `diagnostics report` (`keybinds/Shortcuts.qml`) returns `Diagnostics.report(Compositor, Overlays, Supervision.supervisors, Log.recent())`, built by the pure `utils/Diagnostics.js`: compositor backend and level, present and missing capabilities, the overlay stack (`key on screen`, bottom first) and each screen's surface phases, every supervisor with status, restarts, failures in a row and the last failure, and the recent log with clock times and repeat counts. The backend name appears there for people only; no feature branches on it.

## Frame debugger

`KP_0` (global shortcut `vados:frames`, IPC `frames toggle`) freezes the shell so one frame of one animation can be pointed at. `state/FrameDebug.qml`:

- **Hold.** `Motion.isHeld` is the one pause flag. Every top-level animation in `components/` and `modules/` declares `paused: Motion.isHeld && running` (`tools/check-rules.py` fails otherwise; `tools/animations.py` finds them). The `running` term matters twice: Qt warns when an idle animation is paused, and an animation that starts while held re-evaluates the binding and pauses at once. Qt clears `paused` when a running animation is restarted, so while held the `heartbeat` (a `FrameAnimation`, which also keeps the animation clock ticking) calls `Motion.holdAgain()` every frame, and `Lifecycle.send` calls it once more through `Qt.callLater`: an animation triggered during the hold starts frozen at frame 0.
- **Step.** `step()` clears the flag; heartbeats are ignored until `arm()` has run (a queued call, so Qt has registered the resumed animations), then their times are added up. The heartbeat sits earlier in the Qt animation list than the resumed animations, so the beat that sees at least `Motion.frames.stepMinimum` (12 ms) advanced pauses them again before they update in that tick: exactly the ticks counted have run (one 60 Hz frame; two on a faster display). `Motion.frames.stepTimeout` resumes by time if the clock stops (logged).
- **Back.** Animations cannot run backwards, so each frame reached (frame 0 of a new animation and every step) is also grabbed as a picture: `captureRequested(token, scale)` makes every `FrameTap` (one per window: the taskbar and each `OverlayWindow`) `grabToImage` its content at `Motion.frames.scale` (1, full resolution) times the screen's `devicePixelRatio`, so a replayed frame is drawn pixel for pixel, into the `history` entry (`counter`, `label`, `shots`, each shot with its `bytes`). `trim()` keeps at most `Motion.frames.history` entries and at most `FrameDebug.memory` bytes of pictures (`Motion.frames.memory`, 1 GiB), dropping the oldest first and never the newest. A grab result and its `itemgrabber:` url die soon after the callback (older ones then fail with `Protocol itemgrabber is unknown`), so each tap also loads the url into a hidden `Image` (the shot `keeper`, `cache: true`) inside the callback: the pixmap cache then serves the url to `FrameStage` later; `FrameDebug.release` destroys the keepers of dropped entries. `back()` moves `cursor`; while it is before the newest entry the HUD (`FrameStage`) shows that entry pictures on a dark ground over the frozen shell and `counter` reads `FRAME n REPLAY`; `step()` then only moves `cursor` forward and runs nothing, so the animation stays at its newest frame.
- **Screenshot.** `snap()` (works held or not) asks the taps for a full-resolution grab (`captureRequested(token, 1)`) and, once every grab answered (`pending`), emits `snapshotReady(shots)`; or reuses the entry being replayed. `FrameWindow` lays the pictures out in the hidden `FrameStage` of its HUD, grabs that, saves it with `Quickshell.cachePath` and pipes it to `wl-copy --type image/png`; `finishSnap()` ends it. Only the shell windows are in it.
- **Names.** `utils/Playing.js` is a `.pragma library` registry: a `Lifecycle` plays `<name> <phase>` while moving, `Mutate` plays `<label> enter` or `<label> leave`. Hosts set `label` on `Burst` and `Mutate`; the HUD lists the names (`x3` for duplicates). `frame` counts steps since the current set of animations started and is 0 when it begins.
- **Playground.** `play.qml` grabs its `scene` item, not the window, so the HUD is not baked into the pictures. Its HUD takes the keyboard while held (`holdKeyboard()`, again whenever something else takes it, such as search opening) and hands it back when released (`returnKeyboard()`). `play.py` runs the window in-process: an event filter turns `Num 0` and `Num +` into `pressShortcut("frames" | "frameShot")` before any item sees them, as the compositor's global shortcuts do in the shell, and `shotSaved(path)` puts the screenshot on the Windows clipboard.
- **Not held:** `Timer`s (the taskbar stagger timers), `Behavior` animations (Qt refuses to pause them: `setPaused() cannot be used on non-root animation nodes`) and anything that reads the wall clock keep running. `Lifecycle.watchdog` waits while held.
- **HUD.** `FrameWindow` is a transparent click-through window on the Overlay layer on the screen that pressed the key, visible while held or snapping, with the keyboard while held; every `OverlayWindow` drops its exclusive keyboard while `FrameDebug.isActive`, so stepping works over search (whose field would otherwise take the arrows), settings and the dashboard alike; `modules/framedebug/FrameHud.qml` maps Up and Right to `step()`, Down and Left to `back()`, Plus to `snap()`, Escape to `close()`.

## Reduced motion

`Motion.isReduced` (`motion.reduced`, settings Settings tab) and `Motion.pace(duration)`, the single precedence function: every duration in components and modules goes through it and is 0 under reduced motion. `Rising` stops emitting (`isEmitting`) and `Burst` has no splashes or crests. `TypedText` and finger-driven motion are content and keep their timing; `Motion.reveal.dwell` is an interaction timer, not motion.

## Interruptions

Surfaces go through their `Lifecycle` (§ Transition lifecycle). `Mutate` re-enters from its current pop (`holdPop`). `Burst` reopened during its leave, before the hand-off (`canRewind`), rewinds the leave (`rewinding`, exit back to 0 over the time already spent) and resumes the enter from the spread and impact it had reached (`resuming`), instead of converging from an empty ball again.

## Settings

## Dashboard

`DashboardWindow` is a full-screen overlay layer per screen (namespace `vados-dashboard`, exclusive keyboard while open). It opens from a click on the taskbar clock (`Taskbar.dashboardRequested`), the Hyprland shortcut `vados:dashboard` or IPC `dashboard toggle`, all through `Overlays.toggle("dashboard")`. Search, settings and dashboard are mutually exclusive.

Data: two `Binding`s set `Hardware.isActive` and `Weather.isActive` while the window is open, so hardware polling (`Motion.dashboard.poll`) and the weather fetch (only when older than `weatherPoll`) run only then.

Liquid: one `LiquidLayer` over the whole screen. Inside it one `Upright`-mirrored item holds the `Burst` ability (the body and every drop of its enter and leave) and `Rising`, laid out for the left edge. The body keeps `rootCorner` on the taskbar side and `corner` on the front. Content is placed with `placeX`, which mirrors whole columns so the processor column always sits nearest the taskbar. The dashboard drives no timeline itself: `Burst` plays from `isShown`, content shows on `burst.isOpened`, bubbles run on the same flag, dim is a `Behavior`.

Enter (`components/Burst.qml`, about 0.8 s):

1. **Converge** (`converge`, linear: the nearest part moves on frame 1): every taskbar part flies to the seed point (the taskbar column, `seedX`, at the overlay's height), nearest first (`convergeLag` delays the farthest). A long part first retracts into a circle of its own width (`shrinkShare` of its progress, scaled by how much longer than wide it is, so the task pill needs the most and a circle none), then flies in (`travelStart`), and is swallowed by the ball as a circle shrinking to nothing (`absorbShare`). There is no ball before: the ball is only the mass that has arrived (`ball · √arrived`), so it is born from the parts.
2. **Charge**: the ball inflates and squashes (`impactShare`, `inflate`, `squash`).
3. **Bounce out** (`spread`): width and height follow the `burst` character (`Liquid.rise`, launched at `expansion` so it is `1 − e^(−σt)·cos(ωt)`), over the spread's seconds. The height leads (`heightLead`), so the body first stands up between the top and bottom walls, then shoots out along the dashboard, overshoots the far wall by about 15 % and snaps back, stretched thinner while overshooting (`drag`). The root side settles onto the root wall early (`rootShare`).
4. **Waves crash**: when the height first reaches its walls one wave per side (a single `Shape` bump, `crestLength` long, drawn along the wall path by `wallPoint`) starts at the root on the top and bottom walls, runs along it, wraps round the far corner curve and meets the other on the far wall at 50% height (`crestRun`). The meeting starts `impact` (its own timeline, paused until `meetShare` of the spread): the two halves fuse into one mound that swells and sinks into the body, a jet droplet leaps off the far wall and falls back, and the body bounces like a puddle hit by a drop (far wall dents in then out, height the other way, damped: `impactPush`, `impactCycles`, `impactDamping`). A droplet also splashes off each far corner (`splashSpan`).
5. **Steps**: two rectangles in the liquid give the body a step: the top from the root to `stepTopShare` of the width rises `stepTop` above it, the bottom from the root to `stepBottomShare` drops a bigger `stepBottom` below it. Both scale with the body height, so they grow in and shrink away with it. While they show (`isStepped`), the root `Lobe` grows by their rises (`aboveRise`, `belowRise`) and shifts its centre, so the edge curve covers the steps too. With `hasSideStep` (the host sets it when `Battery.isPresent`), a third step (`stepForm("side")`) grows out of the far wall, `stepSide` deep and `stepSideHeight` tall, centred on the middle, from the moment the waves meet until the overshoot ends (`spread` from `meetShare` to 1), so it lands with the body's bounce. It rides the impact wobble with the wall.
5. Content `Turn`s in by distance from the root (`Motion.dashboard.reveal` ms per px) once `openShare` (0.14) of the spread has passed; `Rising` bubbles leave the top and bottom surfaces.

**Rounded corners**: where the flat top or bottom meets the far wall, `Burst.roundedOutline` cuts the corner into an arc (`Geometry.roundCorners`): radius from the front corner (`form.right`) towards `edgeRound` as the wall grows, fading to 0 within `edgeRoundFade` of a screen edge so the corner melts into it; the body's height closes the last `edgeSnap` pixels to the screen edge by itself, so the top and bottom merge with the edge instead of leaving a sliver. Without the rounding the polygon that replaces the rectangle once the wall exists had square corners (a straight edge on the ball, 2026-11-09).

**Root fused to the edge**: the whole root side is a `Lobe` (the search lobe shape) from past the screen edge (`edgePad`) to `rootSpan` inside the body, flaring wider at the edge by `rootSwell` (scaled by `swellShare` while small), so the dashboard curves into the screen edge the way the search band does. It follows the body through enter and leave. The crest track starts at the screen edge and runs over this flare (`Lobe.bendAt`, sampled every `curveStep` pixels) before the top and bottom edges. **The wave skips the screen edges**: every crest and trough offset is scaled by `freeShare(point)`, 0 within `Appearance.burst.edgeHold` of the taskbar edge, the screen top or the screen bottom (`screenHeight`, set by the host), rising to 1 over `edgeFade`. So the dashboard's wave fades in as its root flare leaves the edge, and search's full-height column shows it only on the far wall, never along its top, bottom or root.

Leave (own, faster; user, 2026-11-09: the taskbar comes out of the closing overlay, as it went into it on the enter):

1. **Collapse**: content out, bubbles drain, a short hold (`leaveHold`), then the body scales down to the `leaveBall` circle at the taskbar column with its root side on the screen edge (`exit` to `leaveShrink`, OutCubic collapse).
2. **Release** (`releasing`, `release` 0 → 1 over `Motion.burst.release`, linear): every taskbar part it took (`parts`, the gear included) leaves the ball as a circle of its own width, all at the same frame (no lag), grows to full size within `releaseEmerge` of its travel, flies to its place (`releaseTravel` of the release, an ease-in-out, no bounce, so no part has covered much of its way after one frame) and starts extending `releaseExtendLead` (about two frames) before it gets there, so the stretch to full length is already under way on arrival; it extends to its full length (the task pill stretches from a circle into the pill) over `releaseExtendSpeed` (0.7) of its span ending at its arrival, with `Geometry.rebound` (`releaseRebound`) so it overshoots a little and settles; the entries are not delayed, since arrival stays where it was. The idle pills keep the released circle as their body and show their icons one after another, the first on arrival (`Mutate.hasArrivalPop`, `Motion.reveal.arrivalStagger` per order after the first). A part arrives when its extension is done (`arrivalOf`: `releaseTravel` for a circle, 1 for the longest part), so the circles arrive first, the activity pill next and the task pill last. The ball is only the mass not yet released (`leaveBall · √(1 − releasedArea)`, by travel), so it necks into the parts and drains as they leave.
3. **Hand-over, part by part**: `Overlays.placeVisitor` gives the taskbar back as soon as the release starts (`release > 0`), and `Taskbar.isArriving` is true from then on. Each pill's `Mutate` waits at size 0 (`wait()`) until its own part has arrived (`hasArrived`, from `visitor.arrivals` through `Taskbar.hasArrivedAt`), then jumps to full size (`arrive()`) and its icons, satellites and splits play in at once (task items after a random delay up to `Motion.reveal.arrivalScatter`). At `release` 1 `landed()` ends the overlay.

Without parts (the `bare` style, or another overlay was open first) the old leave runs (`leave`): the body shrinks to the ball while sliding out past the edge (quadratic travel), and the taskbar comes back at the hand-off below.

**Touching the taskbar on leave**: while leaving, `Burst.visitor` (`{ x, y, width, height, isHandedOff, hasReleased }`, left-edge coordinates) goes `Dashboard.visitor` → the window → `Overlays.placeVisitor` → `TaskbarWindow` → `Taskbar.visitor`. `Taskbar.touchOf(centerX, top, bottom, halfWidth)` gives each task pill and idle circle a 0–1 closeness to it (within `Appearance.taskbar.visitReach`), which swells the pill by up to `visitSwell`. In the release leave the taskbar is away until the parts have landed, so nothing is handed off; without parts, once it has become the ball (`exit >= leaveShrink`) it is handed off (`canHandOff`, from `OverlayWindow`: off for the `bare` style, whose liquid is invisible, and off while a window covers the taskbar; `Burst` copies it into `shouldHandOff` when the leave starts, so a cover that changes mid-leave never moves the body between windows): `Burst` stops drawing it and the taskbar draws the same ball and edge lobe in its own `LiquidLayer`, so it goos and necks with the pills it passes. The windows are separate layers, so a shape can only fuse with the pills inside the taskbar's own layer.

With no parts (another overlay was open first) the ball grows from nothing on `merge` alone.

The earlier wave enter (a travelling `PathPolyline` ripple, crest bulge, idle ripple while open) is shelved in `shelf/dashboard-wave/` for later use.

## Search

`SearchWindow` (overlay layer, exclusive keyboard) hosts the `Search` module. Search is built on the dashboard's foundation: the same `Burst` ability inside an `Upright`-mirrored item, the same `bodyClip` content clip, the same leave and taskbar hand-off (`visitor` → `Overlays.placeVisitor` (keyed by overlay, read back with `visitorOn(screen)`), `canHandOff` off for `bare`). The `Burst` form is the base column: `Appearance.search.widthShare` (20 %) of the screen wide, the full screen height, `hasSteps: false`, `rootCorner` on the taskbar side, seeded at the taskbar column at mid-height.

The far wall (from the user's second sketch, 2026-11-06) is part of the `Burst` body: Search passes `wall` (points traced from the drawing, `Appearance.search.wall`, converted to `[x offset from the full far edge, y share]`) and `Burst` draws it in its own liquid. Each point sits at `formRight + offset × wallShare`, `formTop + share × form.height`, so the wall grows, squeezes and bounces with the body every frame. `wallShare` is the body's width progress after the impact (it overshoots with the bounce) and collapses with the leave. `Burst.traceSpline()` turns the points into one Catmull-Rom outline (`wallOutline`, a sample every `Appearance.burst.curveStep` pixels of each span, `curveSlack` covering the bend), so the wall is a single S-wave. Rounded corners on the track (arc segments) are sampled the same way. The crest and trough push each point along its segment's normal; where segments meet at an angle `joinPoints` sweeps the normal round the corner (a round join), and within `seamBlend` of mid-height, where the top and bottom tracks meet, the normal turns level and the offset fades out, so the two halves meet without a notch. The body and crests are filled with `WindingFill` through the `CurveRenderer`, so they are antialiased and small offset loops never cut holes. The wall: in near the top, out round the best match, in again near the bottom, flaring at both screen edges. The fill starts `form.right` inside the column edge, so the body's corner never shows a notch.

**The split** (notifications menu): `split` runs 0 → 1 over `Motion.burst.split` (OutBack) from `waveShare` of the spread (the moment the edge wave starts, so the same wave runs along the gap edges, `cutHead` and `cutWave`), so the body is whole while it opens and inside the focus budget. `splitShare` is `split` while entering and the held split closing over the first `splitClose` of the exit while leaving; a rewind resumes it. The gap is `splitGap * splitShare` around `splitAt` of the form height; `trace()` cuts `bodyOutline` with `Geometry.splitAlong` into `bodyPieces` (one `PathMultiline`) and each crest the same way into `crestPieces`, and the root `Lobe` hides while split (the outline already holds the root bend), so the gap reaches the screen edge. A body without a wall never splits.

A walled body is one polygon (`bodyOutline`) traced along the top and bottom tracks (`topTrack`, `bottomTrack`, shared with the crest; all three, and `crests`, are written by `trace()`, queued once per frame with `Qt.callLater`), with the wave's troughs cut into it beside the crest; its wall ends curve inward until `flare` turns them outward into the screen edges after the bounce; With a wall, the burst's crest runs along `wallOutline` instead of the plain far side, the jet leaves from the wall at mid-height (`farFront`) and the corner splashes leave from the wall's ends. Search reads `burst.wallOutline` for `wallReach`; the click bands (`wallBands`, one `MouseArea` each) come from the settled wall (`settledWall`), so the `Repeater` is not rebuilt every frame; `presence` (`bud` × `wallShare`) only drives content (row shortening).

Content, placed with `edgeX` (mirrors to the right edge):

- **List** (`ResultRow`, in `bodyClip`): every result after the best match, from the top to the field; while the field is empty, favourites (`search.favorites`, as they were when the search opened) come first. The `ListView` model is a `ListModel` of app ids that `syncList` edits in place unless the query changed. Rows scrolled up past the top fade over `topFade` (`fade`), shrink by `rowShrink` and lose their name first. Rows beside the best match get a `room` from `Search.rowRoom(rowTop)` that ends `lobeGap` before its circle, so the name elides at the end; that part has no fade.
- **Best match** (`FoundCard`): a circle (`found`, wash fill, `ringStroke` ring, accent while selected) with the icon (`foundIcon`) inside, at `foundX` from the root and `foundShare` of the height. Its name is in a liquid pill outside the wall (`nameReach` past the wall's widest point), joined to the circle by a `tether` line. The pill is a `LiquidShape` in Search's liquid layer sized from `FoundCard.nameSpan` / `nameThickness`, so it necks with the wall; `FoundCard.bloom` (a `Behavior`, OutBack in over `Motion.search.nameGrow`, InQuad out over `nameShrink`) grows it from a droplet at the wall side to the far side, its height opening from the vertical middle first (`nameHeightLead`), and the name is revealed by the clip.
- **Field**: the wash pill at the bottom of the column, with the result count and the search glyph on its right.

Content `Turn`s in by distance from the root (`Motion.search.ripple` ms per px, plus a row stagger); while typing, new rows use only `settledStagger`.

Keys: arrows move inside a zone. From the best match, toward the taskbar or down goes to the list, away from it or up goes to the profile. From the list, away from the taskbar goes to the best match. In the profile, up and down step through the picture and the power buttons, toward the taskbar goes back to the best match. Directions mirror with the side. Tab and Shift+Tab cycle the zones; Enter launches or activates; Escape clears the query, then closes. The Menu key opens the app menu on the selection (right click opens it at the pointer); while it is open, Up, Down and Tab move in it, Enter chooses and any other key closes it. Ctrl+H flips HIDDEN, the grey toggle under the field: hidden apps (`search.hidden`) are left out of every result until it is on, and show faint while it is.

**Overlay swap** (2026-11-09). Opening an overlay while another one is showing on the screen is a swap (`Overlays.swaps`, per screen). The first (`isHandingOver`) leaves without giving parts back (`Burst.isSwapped`, latched at the start of its leave): it collapses to a circle of `look.ball` at the taskbar column, hides itself at `leaveShrink` and lands. The next (`isWaiting`) stays hidden until that landing (`settleSwap`), then starts from the circle (`hasCircle`: `merge` is 1, no converge), so the two bodies never overlap and the taskbar stays away. The swap ends when the next one is active or closed.
