# Security and privacy rules

Enforced by `tools/check-rules.py` where marked ✓.

- **The lock screen fails closed.** The session lock (`WlSessionLock`, ext-session-lock) lives only in `windows/LockWindow.qml` ✓ and authentication (`PamContext`) only in `services/Lock.qml` ✓. Unlocking never waits on an animation; the liquid on the lock screen is decoration that can fail without effect. A shell crash leaves the session locked (the protocol guarantees it; never use a plain overlay as a lock); driftwm's support was confirmed in its source (2026-11-14). **The session locks only on request** ✓: `LockWindow`'s `locked` binds `Lock.isLocked` and nothing else, it starts false, and only `Lock.lock()` sets it. A request (`Lock.request()`) plays the lock enter over the desktop first and locks once it covers every screen, never later than `Motion.lock.engageWait`, whatever the enter does (user, 2026-11-17); the crash marker is written at the request. A reload while locked would unlock, so the shell stops watching its files while locked. There is no unlock without PAM (no IPC unlock).
- **The network is reached only from files listed in the README Network section** ✓, and only while the feature that needs it is on screen. No telemetry, no update checks, no font or icon downloads.
- **Secrets never touch disk.** The clipboard history skips entries offered with `x-kde-passwordManagerHint: secret` and entries from password managers; nothing secret goes into `~/.cache/vados` or `shell.json`.
- **Changing the boot is opt-in and asks every time** (user, 2026-11-17). SPLASH and PLYMOUTH start off; each switch runs `scripts/boot.py apply` through `pkexec` (one admin prompt per change, never a stored grant), the script refuses any path outside the boot setup (`rules/state.md`) and a failed rebuild restores every file and rebuilds again, so the machine never stays on a half-written boot. Nothing changes on start or reload: only a press on the switch does.
- **Passwords asked by the shell never touch disk or the log** (2026-11-18). The password prompt passes a polkit password only to `AuthFlow.submit` and a keyring password only over `keyring.py`'s stdin, which hands it to the caller through the keyring's secret exchange; neither is kept after the answer.
- **Taking over system roles is opt-in.** The notification daemon (`notifications.enabled`) and any later role (polkit agent, clipboard owner) start off and say in the README what they replace. The clipboard history is not such a role: it only watches the clipboard, so it is on by default (user, 2026-11-11).
